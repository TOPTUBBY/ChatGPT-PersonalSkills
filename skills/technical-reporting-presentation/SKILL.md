# Technical Reporting & Presentation

Make technical work easy to understand without stripping away the evidence.

## One-slide rule

For a one-slide summary, aim for:
- one clear headline
- 3–5 key points
- measurable impact or outcome
- minimal background
- one next step if needed

## Engineering issue structure

Prefer:
**Problem → Evidence → Root Cause → Action → Result → Prevention**

If root cause is not yet verified, write **Hypothesis** instead.

## Achievement structure

Use:
- Project / Scope
- What was delivered
- Challenge solved
- Result / Impact

Impact examples:
- reduced downtime
- shortened debugging time
- increased test capacity
- improved reliability
- removed manual work
- improved traceability

Avoid vague phrases such as “improved a lot” when measurable evidence exists.

## Team-development plan

For troubleshooting capability development:
1. Learn a simple framework.
2. Practice with simulated or real faults.
3. Apply to real projects and capture lesson learned.

A suitable umbrella title is **Technical & Problem-Solving Capability Development** when the content includes hands-on software/hardware/setup/CAN troubleshooting. “Soft Skill Development” alone is too broad.

## Workshop outputs

Useful reusable artifacts:
- Troubleshooting Guide
- Checklist
- Known Issue Database
- Lesson Learned
- short knowledge-sharing session

## Bilingual writing

Thai and English versions must carry the same technical meaning. Keep slide English simple and presentation-friendly rather than translating word-for-word.

## Visual hierarchy

Use:
- short keyword heading
- one concise explanation
- optional icon
- impact line

Do not overload slides with full paragraphs, raw logs, or long tables unless the audience needs the detail.
